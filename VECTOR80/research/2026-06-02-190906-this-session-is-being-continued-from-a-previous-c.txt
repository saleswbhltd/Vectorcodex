  1. The CSV is lying to you

  The trades CSV says +4,769 pips, 76% win rate. The official MT5 HTML report
  says -12 pips, 20.5% win rate.

  Root cause: when a buy/sell limit expires or is cancelled, CJournal is writing
   a fake TRAIL close row at the cancellation moment, using the live market
  price as the "close" — which puts price far from the never-filled limit and
  counts as a phantom win. Example from the events file:

  00:05:00 ORDER_PLACED #2 BUY @ 1.02117 ...
  00:05:00 CLOSED       #2 @ 1.02397 Reason:TRAIL Pips:28.0   ← never filled,

  170 of the 189 CSV "trades" are these phantom TRAILs. That's also why the
  earlier "1213 trades, 68% WR, +$28k" number from the mixed log was bogus —
  same bug.

  an order actually filled and then closed — i.e. PositionClose, not

  Architecture summary

  The EA is a single ~600-line file with five layers:

  1. CM5ZigZag class — pip-threshold ZZ on M5; warms up from 500 historical bars
   on OnInit, then processes one new bar at a time. Emits a confirmed pivot via
  Consume().
  2. PassesQualityFilter() — applies G1+G3+G6 at the pivot bar; returns reason
  string so you can see filter decisions in the log.
  3. g_monitors[16] — multiple pivots can be waiting for M1 trigger
  simultaneously. Each monitor watches its trigger price; fires OpenPosition()
  when M1 low/high crosses; aborts after InpMaxWaitM1Bars bars.
  4. g_positions[16] — tracks each open position's entry_price, current_sl,
  max_favorable_pips. On every tick: updates max-favorable, moves SL forward
  when better, closes at timeout.
  5. Visual panel + arrows — arrows drawn on confirmed-and-filtered pivots so
  you can verify behaviour visually before going live.

  How to test

  1. MetaEditor → open VECTOR002.mq5 → F7 to compile (it'll complain if
  anything's off — paste me errors).
  2. Strategy Tester → Expert: VECTOR002 → Symbol: EURUSD → Timeframe: M1 (so
  trail/entry tick on M1) → Modelling: every-tick-based-on-real-ticks → Inputs →
   Load VECTOR002.set.
  3. Date range: 2026.01.01 → 2026.06.01 (matches the research window).
  4. Run.

  - ~100–110 trades total
  - 70%+ win rate

  What's in the logs

  Two CSV files per backtest run, written to \MQL5\Common\Files\. Per-run
  timestamping (using TimeCurrent() at OnInit) means each test gets its own pair
   — no append accumulation.

  VECTOR002_trades_YYYYMMDD_HHMM.csv

  One row per closed trade — 24 columns:

  Identity: ticket, symbol, direction
  Pivot context: pivot_time, pivot_price, confirm_time, confirm_lag_m5,
    atr_at_pivot, d2low_at_pivot
  Monitor: monitor_start, trigger_price, m1_bars_to_trigger
  Entry: entry_time, entry_price, initial_sl
  Close: close_time, close_price, close_reason
  Result: lots, pips, usd
  Mgmt: max_favorable_pips, trail_moves, hold_minutes

  Lets you slice every dimension that mattered in research: "did wins come from
  low-confirm-lag pivots?" "did the trail trigger more often on SELL?" "did the
  M1 trigger fire faster on profitable trades?"

  VECTOR002_events_YYYYMMDD_HHMM.csv

  Lifecycle events, 6 columns: timestamp, event, ticket, direction, price, note

  Event types you'll see:
  - EA_START / EA_STOP — bookends with inputs and reason
  - PIVOT — every M5 ZZ pivot, before filtering
  - FILTER_PASS / FILTER_FAIL — with the reason (G1 fail: atr=4.2, etc.)
  - MONITOR_ADDED — when filtered pivot starts watching M1
  - MONITOR_TIMEOUT — pivot abandoned after 60 M1 bars with no trigger
  - MONITOR_FULL — pivot dropped because all 16 monitor slots in use (raise
  MAX_MONITORS if frequent)
  - ENTRY — position opened, with trigger price + bars waited
  - ENTRY_SKIP_MAX / ENTRY_SKIP_LOTS — entry blocked
  - SL_TRAIL — every trail SL move
  - SL_MOVE_FAIL / ORDER_SEND_FAIL / etc. — broker rejections
  - CLOSED — with reason (SL_HIT / TRAIL_HIT / timeout)

  Close-reason inference

  - timeout — we closed it ourselves at +60 min
  - TRAIL_HIT — broker closed via stop AFTER we'd trailed at least once (a
  profitable lock-in)
  - SL_HIT — broker closed via the initial SL (no trail had moved)

  Determined by querying HistorySelectByPosition for the actual close deal — so
  close_price is real fill price, not theoretical.

  Why tick features helped SELL_SWING specifically

  SELL_SWING is the most "exhaustion-driven" pivot type — top of a rally,
  momentum dies. Tick-level features that capture this:
  - tick_velocity_first_half vs tick_velocity_second_half — momentum dying
  within the bar
  - bid_aggressor_pct falling — buying pressure exhausting
  - ticks_at_high_pct high — price spent time at top before reversing
  - max_run_up_pips_intrabar vs net bar change — rejection signature

  These were INVISIBLE in M5 aggregated indicators.
